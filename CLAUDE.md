# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

HuaEBL is an all-in-one, mobile-friendly e-learning web app. Bun-workspaces monorepo:

- `apps/web` — Vue 3 + Vite + TypeScript, Tailwind v4 + shadcn-vue, Pinia, Vue Router, `lucide-vue-next`
- `apps/api` — ElysiaJS on Bun, Drizzle ORM (PostgreSQL via Bun's native SQL driver), exports `type App` for the web's Eden Treaty client (`@hua/api` workspace package)

Login is delegated to **TekSso** (`/home/voidkle/Documents/Github/teksso`, OAuth2 authorization-code, backend-for-frontend; its README has the endpoint contract). Roles live in this app's own `users` table (keyed by TekSso id), not in TekSso.

## Commands

```bash
bun install                                  # from repo root
bun run api                                  # API on :4000 (bun --watch)
bun run web                                  # Vite on :5173
cd apps/api && bun test                      # API smoke test (no DB needed)
cd apps/api && bun run typecheck             # tsc
cd apps/web && bun run typecheck             # vue-tsc (also type-checks apps/api via Eden)
cd apps/web && bunx shadcn-vue@latest add <component> --yes --overwrite </dev/null   # stdin MUST be closed or the CLI hangs; afterwards run
#   grep -rl 'from "cn"' src | xargs sed -i 's|from "cn"|from "@/utils/cn"|'   (CLI mis-writes the cn import because of the utils alias). The CLI also re-adds `@lucide/vue` (run `grep -rl '@lucide/vue' src | xargs sed -i 's|@lucide/vue|lucide-vue-next|' && bun remove @lucide/vue`) and overwrites `button/Button.vue` + `button/index.ts` (re-apply the compact sizes, see Web UI)
cd apps/api && bunx drizzle-kit generate     # SQL migration from src/db/schema.ts -> apps/api/drizzle/
cd apps/api && bunx drizzle-kit push         # apply schema to the DB in DATABASE_URL (shared remote dev DB: review the diff first; needs the `pg` dev dep, the app itself uses Bun SQL)
```

Env: copy `apps/api/.env.example` → `apps/api/.env` (DATABASE_URL with URL-encoded password, `SESSION_SECRET`, TekSso client id/secret from TekSso's Apps page with redirect URI `APP_URL/auth/callback`, `BOOTSTRAP_ADMIN` = TekSso username auto-promoted to admin on sign-in, optional `UPLOAD_DIR` for the logo, default `apps/api/uploads`, git-ignored; needs a persistent volume in production). `apps/web/.env`: `VITE_API_URL`. Never commit `.env` or put credentials in tracked files.

## Auth architecture

`apps/api/src/modules/auth` implements TekSso's BFF contract: `/auth/login`, `/auth/callback`, `/auth/logout`, `/auth/logged-out`, `/auth/me`. The session is a **signed cookie** (`hua_session` = `{id}` of the local user; `hua_sso_state` during login), configured on the root app in `src/index.ts`. Routes are guarded with the macro in `src/plugins/auth.ts`: route option `role: true` (any user) or `role: ["admin", "operator"]`; it reloads the user from the DB per request (role changes apply immediately) and gives the handler a non-null `user`. Unverifiable cookies → 401 and the cookie is expired (`plugins/error.ts`). New TekSso users default to `student`. Roles: admin, operator, teacher, staff, student. Signing in needs `TEKSSO_CLIENT_ID`/`TEKSSO_CLIENT_SECRET` (empty ones make `/auth/login` answer 503 naming them, and TekSso itself would answer a misleading `unsupported_grant_type`) **and** the TekSso user must be granted the app (TekSso: Users → Edit → App access), otherwise TekSso answers 403 "You don't have access to …". TekSso's login page is a separate Vite app (`teksso/frontend`) at its `FRONTEND_URL`: run it on a port other than this app's 5173 (the dev setup uses 5175).

## Web UI

Style reference: light, compact, Linear-like. The sidebar sits on the page background (`--sidebar`), the content is a rounded white inset panel (`--background`), board columns/chips use `--muted`, cards are `--card` with thin borders and `shadow-xs`; text is Inter at 13px/12px; the active nav item is a white pill; page sections use underline tabs. Primary is the ink `#333446` (`#B8CFCE` in dark mode).

App shell = `components/layout/AppShell.vue` (shadcn `SidebarProvider` + `Sidebar variant="inset"` + `SidebarInset`), the parent route of every signed-in page; the sidebar becomes a drawer on mobile. Sidebar items live in `components/layout/navItems.ts` (`navGroups` + bottom `footerItems`, filtered by role; items without `to` render disabled with a "Segera" badge — add `to` when the feature ships). Page titles come from `route.meta.title`.

The shadcn primitives in `components/ui/` are owned code and were compacted by hand (Card padding/gap, Button sizes h-8/13px, sidebar menu text 13px): re-apply these if you run `shadcn-vue add --overwrite` on `card`, `button` or `sidebar`.

Theme: palette `#333446 / #7F8CAA / #B8CFCE / #EAEFEF` mapped to shadcn tokens in `assets/main.css` (light + `.dark`). `#7F8CAA` fails 4.5:1 as text on light backgrounds, so it is used for borders/rings/charts only and text uses `--muted-foreground`; keep every new text/background token pair ≥ 4.5:1. Dark mode is a `.dark` class on `<html>` toggled by `composables/useTheme.ts` (persisted in `localStorage` key `hua-theme`; an inline script in `index.html` applies it before first paint). Badge/Button `destructive` use white text, which is too faint on the dark-mode red: use `variant="outline"` with `text-destructive`.

The dashboard (`features/dashboard`) is stat cards + an activity chart and shows **placeholder data** from `services/dashboardApi.ts`; replace that one function with an Eden call when the API modules exist.

The web app does full-page redirects to `/auth/login` and `/auth/logout`; `features/auth` holds the store (`useAuthStore`), the router guard loads `/auth/me` once.

## Config module (`apps/api/src/modules/config`, web `features/config`)

Settings live in the key/value table `app_settings` (jsonb values); `service.ts` holds the keys + defaults and is the only place to add a setting (then add it to the `editable` schema in `index.ts`, `types.ts`/`useConfigForm.ts` on the web, and a form field). Endpoints: `GET /config/public` (anyone: site title, copyright holder, logoUrl), `GET|PATCH /config` and `POST|DELETE /config/logo` (admin + operator), `GET /config/logo` (public, cached by `?v=` version). Rules: the AI API key is write-only (the API returns only `aiApiKeySet`; PATCH `""` clears it; stored in plain text, see the `ponytail` note); the logo is PNG/JPG/WebP ≤ 1 MB validated by magic bytes (SVG is refused on purpose: it can carry scripts) and stored at `UPLOAD_DIR/logo`; `logoVersion`/`logoType` are not patchable (Elysia strips unknown body keys instead of rejecting them). `maxEbookMb`, `maxChatMediaMb`, `maxVideoMb` and `maxAssignmentMb` are enforced (e-books, chat attachments, videos, assignment files); `biometricsEnabled` switches presence on (see the Presence module) and `schoolLat/schoolLng/schoolRadiusM` set where check-ins are accepted (null coordinates = no location check; `/config/public` exposes only `biometricsEnabled` and `locationRequired`, never the coordinates; a cleared setting is stored as JSON `null`, not SQL NULL). Video AI settings: `transcriptionEnabled/BaseUrl/Model/Language/ApiKey` (speech-to-text) and `aiSummaryEnabled/aiBaseUrl/aiModel/aiApiKey` (summary), both OpenAI-compatible; both keys are write-only like the AI key (`transcriptionApiKeySet`), and `/config/public` exposes `maxVideoMb`, `transcriptionEnabled` and `aiSummaryEnabled` so the UI can explain a disabled button.

Web: `useBrandingStore` (title, copyright holder, logo) is loaded in the router guard before the first navigation and updated live on save; the sidebar brand, login page, `AppFooter` and the tab title (`App.vue`) read from it. Footer text is `© {current year} {copyrightHolder}. Powered by huaEBL by ruthkle. All rights reserved.` (only the holder is editable; year is automatic). The form's draft/patch logic is in `useConfigForm`; logo upload/removal save immediately, everything else on "Simpan". Route `/config` is limited by `meta.roles`.

## Mading module (`apps/api/src/modules/mading`, web `features/mading`)

Table `notices` (title, body ≤ 2000, author, status `pending|approved|rejected`, reviewer, `review_note`). Rules live in `service.ts`: posts by student/teacher start `pending`; posts by staff/admin/operator (`REVIEWERS`) are published immediately; only reviewers approve/reject (route-level `role: REVIEWERS`); reject takes an optional note shown to the author; visibility = approved for everyone, plus the author's own, plus everything for reviewers (hidden notices answer 404, not 403); only the author edits, and a non-reviewer's edit sends the notice back to `pending` (even if it was approved); the author or a reviewer deletes. Web: `MadingView` wires `useMading` (permissions mirror the API's rules for showing buttons only; the API is the authority) to the board, `NoticeFormDialog`, `NoticeRejectDialog` and `NoticeDeleteDialog`. No realtime/pagination yet (newest 200).

## E-book module (`apps/api/src/modules/ebooks`, web `features/ebooks`)

API: PDFs at `UPLOAD_DIR/ebooks/<id>.pdf` (+ `<id>.cover`), tables `ebooks` and `ebook_progress` (last page per user, clamped to `page_count`). Upload (`POST /ebooks`, multipart) is limited to `UPLOADERS` (admin, operator, teacher, staff); everyone signed in can read everything. The upload enforces the **configurable `maxEbookMb`** (413 with the limit in the message; the public config exposes it so the dialog can pre-check) and checks magic bytes (PDF; cover PNG/JPG/WebP ≤ 1 MB); `page_count` is reported by the uploading browser (pdf.js) and is informational. `GET /ebooks/:id/file` honors single `Range` requests (pdf.js then fetches only the pages it needs; the CORS plugin exposes `Content-Range`/`Accept-Ranges`) and is served with `nosniff` + `sandbox` CSP. Delete: the uploader, or admin/operator. Request bodies are capped at `MAX_BODY_MB` (default 256, env) and buffered in memory: the config page allows up to 10,240 MB but the effective limit is `min(config, MAX_BODY_MB)`; stream uploads to disk before raising it for video.

Web: the library is `/ebooks` (inside the sidebar shell); the reader is `/ebooks/:id` **outside the shell** (full screen). `?page=N` opens at that page and beats the saved position (this is the hook for the "Linker" deep links). `useEbookReader` owns book/pdf/page/mode/rtl state, persists mode + RTL in `localStorage` (`hua-reader-mode`, `hua-reader-rtl`) and saves progress debounced (1.5 s, flushed on leave/hidden). Three interchangeable readers share one props shape (`pdf, numPages, aspect, rtl` + `v-model:page`) and expose `next/prev/goTo`: `FlipReader` (StPageFlip; RTL = reversed page list; two-page spread on wide screens, single page on mobile; **never use StPageFlip's `showCover`**: it makes covers "hard" pages that swing like a door and look broken on narrow screens, so every page is soft and invisible placeholder pages (`null` items in `makeItems`) keep the cover alone beside an empty half; the layout is rebuilt when the orientation changes, and a spread is named by its left page in LTR and its right page in RTL), `ScrollReader` (continuous, IntersectionObserver renders pages within one screen and frees canvases beyond three), `PagedReader` (one page, tap zones/swipe/keys). All three render lazily and free canvas memory. pdf.js and its worker are lazy chunks (the shared `src/services/pdfService.ts` is the only importer; the e-book and presentation features both use it, and `PagedReader` is now the shared `src/components/PdfPagedView.vue`, whose `unit` prop names a page "Halaman"/"Slide"); never put pdf.js objects in deep `ref`s (use `shallowRef`/`markRaw`). Pages are assumed to share page 1's aspect ratio. `page-flip` has no types: see `src/types/page-flip.d.ts` (import from `page-flip/dist/js/page-flip.module.js`).

## Chat module (`apps/api/src/modules/chat`, web `features/chat` + `services/socketClient.ts`)

Data: `chat_rooms` (direct | group; a direct pair shares exactly one room via `direct_key`), `chat_members` (`last_read_message_id` drives unread), `chat_messages` (text, one optional attachment, one optional link, soft delete). Anyone can DM anyone and anyone can create a group; membership is fixed after creation. Sending is a normal multipart `POST /chat/rooms/:id/messages` (saved first, so nothing is "sent" that isn't stored); **live delivery is a WebSocket** (`/chat/ws`): the session cookie authenticates the handshake through the same `role` macro, the `Origin` header must equal `FRONTEND_URL` (cross-site WebSocket hijacking), each socket subscribes to `user:<id>`, and `service.ts` publishes `message` / `deleted` / `room` events to every member via `realtime.ts` (the server handle is set in `onStart`; with `app.handle()` publishing is a no-op). Clients ping every 25 s and reconnect with backoff; on every (re)open the store re-syncs rooms/unread and an open room re-fetches the latest page. Dedupe key = message id (the sender receives their own message both from the HTTP reply and the socket). **`app.handle()` cannot test sockets: use `app.listen(0)` and a real `WebSocket`.**

Attachments (`UPLOAD_DIR/chat/<messageId>`): type is detected from the bytes (never the declared MIME or extension); only browser-native image/video/audio types are served inline (with Range, so video seeks), everything else is a forced download (`octet-stream` + `attachment`, `nosniff`, sandbox CSP); only room members can fetch; the size limit is the configurable `maxChatMediaMb` (413; also exposed in `/config/public` for a client pre-check), effective cap `min(config, MAX_BODY_MB)`. File names are sanitized. Delete = sender, or admin/operator when they are a member; the row stays as "Pesan dihapus" and the file is removed.

**Linker**: a message may carry `linkType/linkRef/linkPage` (`ebook`, where `page` is the page, `video`, where `page` is the second, and `slide`, where `page` is the slide). `/chat/linkables` returns `{ebooks, videos, presentations}`, and the link shape is `{type, ref, page, title, total, hasCover, available}`. The API validates the target and page and resolves title/cover at read time (a deleted e-book shows a greyed card, the message survives). Web: `services/linkTarget.ts` (`linkHref`) is the single place that maps a link to a route; add new resource types there, in `makeLink` validation (`service.ts`), and in `LinkPickerDialog`. Two entry points: the composer's link button, and the "share from this page/minute" buttons of the readers, wired in `pages/EbookReaderPage.vue`, `pages/VideoWatchPage.vue` and `pages/PresentationViewerPage.vue` (a page assembles the feature + chat; no feature imports chat). A video link opens `/videos/:id?t=seconds` and a slide link `/presentations/:id?page=N`; both beat the saved position. A Google Slides/Canva deck has no slide count (`total: null`), so its card says "Dari awal" and the picker asks for no slide number.

Web gotchas: Eden parses ISO date strings into `Date` for REST responses while WebSocket events carry plain strings, so compare/format timestamps via `new Date(x)` (sorting with `localeCompare` crashed). `useChatConnection` (in `AppShell`) opens the socket once for signed-in pages and feeds `useChatStore` (rooms, unread, sidebar badge); `useChatRoom` owns one conversation's messages and unsubscribes on unmount. `MessageList` pins to the bottom (including while images load, via a ResizeObserver), holds position when older messages are prepended, and only loads older pages after the first scroll-to-bottom. Not built: typing indicators, presence, message edit, per-message read receipts, rate limiting (add before exposing to the public internet), push notifications when the app is closed.

## CBT module (`apps/api/src/modules/cbt`, web `features/cbt`)

Tables: `exams` (settings: duration, open/close window, attempts, shuffle questions/options, timer, optional access token, `showScore`, `showReview`), `exam_questions` (+ `exam_options` with `is_correct`), `exam_attempts` (per-attempt `seed`, `deadline_at`, scores, `graded_at`), `exam_answers`. Question types: `single`, `multiple`, `truefalse` (two fixed options Benar/Salah), `essay`. Roles: teacher (own exams), admin/operator (all) manage and grade; only students take exams (`role: ["student"]`); staff do neither. Split by file: `exams.ts` (manage/editor), `attempts.ts` (student flow, finalizing, results), `grading.ts` (results table, grading, CSV), `scoring.ts` + `shuffle.ts` (pure, unit-tested in `cbt.test.ts`).

Rules worth knowing before changing anything:
- **The server owns time.** `deadline_at = min(start + duration, closesAt)` is stored at start; the browser's timer is display only (corrected by the server clock sent as `serverNow`). Answers are accepted until deadline + 5 s grace; after that the attempt is finalized (lazily: on load/save/results listing; there is no cron) with `submittedAt = deadline`. A closed/finished attempt answers 409, which the player treats as "go to the result".
- **Correct answers never reach a running exam**: `loadAttempt` returns questions/options without `is_correct`/explanation. Review data (`getResult`) is only sent when the attempt is graded AND `showReview`; the score only when graded AND `showScore`. (If an exam has no close date, a student with review on could share answers with classmates still taking it: the teacher decides per exam.)
- **Scoring**: single/true-false all-or-nothing; multiple-select = `points * max(0, (right - wrong) / correctCount)` (documented in `scoring.ts`); blank essays score 0 automatically; other essays wait for a manual score (0..points) + feedback. Totals are always *recomputed* from the answers (regrading replaces, never adds). `graded_at` is set once no essay is left.
- **Shuffle** is deterministic per attempt (`seed`, mulberry32), so a refresh keeps the same order; true/false is never shuffled. Questions are **locked once any attempt exists** (409); settings stay editable.
- **Access**: optional token, compared case-insensitively in constant time, only needed to *start* (resuming needs none); a double click returns the same attempt (unique index on exam+student+attemptNo). A closed exam a student never took is hidden from their list.
- **CSV export** (`GET /cbt/exams/:id/export`): UTF-8 BOM, comma separated, cells starting with `= + - @` are prefixed with `'` (formula injection). Opens in Excel/Sheets/LibreOffice.
- **Clock gotcha**: take every CBT timestamp from the app (`new Date()`), never from the DB default `now()`: the remote DB's clock differs by minutes and made attempts "submitted before they started".
- **Drizzle gotcha**: inside a select without joins, `${exams.id}` prints as plain `"id"`, so a correlated subquery resolves it to its own table. Use `outerExamId` (`result.ts`) for subqueries.

Web: managers get `ManagedExamList` → `ExamEditorView` (settings form + question builder with validation that mirrors the API in `services/validateQuestion.ts`; saves settings then questions) → `ExamResultsView` → `GradingView`. Students get `AvailableExamList` → `StartExamDialog` (token) → `ExamPlayerView` at `/cbt/attempts/:id` (**outside the shell**, full screen) → `ExamResultView`. `useExamAttempt` is the heart: autosave queue (150 ms for choices, 800 ms for essays; retries every 3 s; `beforeunload` guard), auto-submit at zero, refresh-safe. Send only the fields that apply to a question type when saving (the API rejects `essayText` on a choice question). `structuredClone` throws on Vue reactive objects: copy explicitly. `unwrap` now throws `ApiError` with the HTTP `status`. `BaseConfirmDialog` takes `:destructive="false"` for non-destructive confirms (e.g. "Kumpulkan"). **Excel import** (`cbt/importXlsx.ts`, web `ImportQuestionsDialog`): `GET /cbt/import/template` builds the .xlsx (sheet `Soal` with one example per type + sheet `Petunjuk`) and `POST /cbt/import/preview` (multipart, managers only) only *parses* the first sheet into questions + per-row errors, so nothing is saved: the dialog appends the questions to the editor draft and the teacher presses Simpan (the existing locked/200-question rules still apply). Columns: Tipe (PG, PGK, BS, Esai, English keys also work), Pertanyaan, Poin (blank = 1), Pilihan A-H, Jawaban Benar (letters like `A,C`; `Benar`/`Salah` for BS), Pembahasan. All-or-nothing: any error blocks the whole import, and each message names the Excel row. Limits: 2 MB, 500 rows, magic bytes `PK`; exceljs loads the whole workbook, so a hostile zip bomb under 2 MB is the known ceiling. Reuses the API's `validateQuestion`. Not built: anti-cheating (tab-switch logging), question bank, per-student or per-class targeting (no classes yet), email/Chat notifications, partial-credit rules other than the documented one.

## Video module (`apps/api/src/modules/videos`, web `features/videos`)

Flat library (no courses/folders). **Needs `ffmpeg` and `ffprobe` on the server** (poster, probing, audio extraction). Files live in `UPLOAD_DIR/videos/<id>/`. Tables: `videos` (status `uploading|ready|failed`, approval `pending|approved|rejected` + `review_note`, duration/size/poster, transcript and summary job status/error, `chapters` jsonb), `video_cues` (the transcript, also what the player's captions are built from), `video_progress` (resume position per user).

Upload: resumable **8 MB chunks** (`POST /videos` creates the row, `PATCH /videos/:id/upload?offset=` appends raw bytes with `parse: "none"`, `GET` returns the offset so the client resyncs on a 409, `POST /complete` verifies size, probes and makes the poster), so the body cap and memory are no issue; the limit is the configurable `maxVideoMb` (413). Only browser-safe files are accepted: `probeVideo` applies per-container codec rules (MP4: H.264/VP9/AV1 + AAC/MP3/Opus, WebM: VP8/VP9/AV1 + Opus/Vorbis; an MKV renamed to .webm is rejected). `/file` honors Range. An unfinished upload (page closed) stays `uploading` and shows as "Unggahan belum selesai": uploads are not resumable across reloads.

Roles: everyone signed in uploads; **student uploads start `pending`** and stay hidden from others (and from `/chat/linkables`) until a teacher/staff/admin/operator (`REVIEWERS`) approves (reject takes an optional note); reviewers' uploads are approved immediately; a non-reviewer's edit sends an approved video back to `pending`; the uploader or a reviewer deletes. Captions: uploader or reviewer can upload `.vtt`/`.srt` (`PUT /captions`, free). **Automatic transcript and AI summary are reviewers-only, button-triggered and never automatic** (they cost money): transcript extracts audio with ffmpeg in `VIDEO_AUDIO_CHUNK_SECONDS` pieces (default 900) and calls the OpenAI-compatible `/audio/transcriptions`; summary sends the transcript (capped at `PROMPT_BUDGET_CHARS`) to the chat-completions API and stores text + timestamped chapters. Jobs run in an in-memory sequential queue (`jobs.ts`); `recoverJobs()` in `onStart` re-queues jobs a restart left half-done. A failed re-run keeps the previous transcript. Provider errors are scrubbed of the API key before they reach the client.

Web: `VideoLibraryView` (cards, filter, upload dialog with progress, approve/reject, delete), `VideoWatchView` at `/videos/:id` inside the shell: native `<video crossorigin="use-credentials">` with a `<track>` served from `/captions.vtt`, speed select (`hua-video-speed`), resume from the saved position or `?t=`, searchable click-to-seek `TranscriptPanel`, AI summary + `ChapterList`, and `VideoManagePanel` (details, caption upload, auto transcript, summary, with the reason shown under a disabled button). `useVideoWatch` polls while a job runs and saves progress. The real STT/LLM providers were only tested against a fake server.

## Presentation module (`apps/api/src/modules/presentations`, web `features/presentations`)

Read-only slide decks, three kinds (`presentations.kind`): `file` (an uploaded **PPTX, PPT or ODP**), `google` and `canva` (a link only, nothing stored). **Needs `soffice` (LibreOffice) and poppler (`pdfinfo`, `pdftoppm`) on the server.** Same roles as e-books: admin, operator, teacher and staff add; everyone signed in reads; the uploader or admin/operator deletes; no approval step. The size limit is the configurable `maxPptMb` (413; also in `/config/public`).

Files: `POST /presentations` (multipart, **either** `file` **or** `link`) detects the type from the bytes (legacy `.ppt` is the generic OLE signature, so it also needs the `.ppt` extension), stores `UPLOAD_DIR/presentations/<id>/source.<ext>`, answers at once with status `converting` and queues a job (`jobs.ts`: in-memory, one conversion at a time because they share one LibreOffice profile, `UPLOAD_DIR/presentations/.lo-profile`). `convert.ts` runs headless `soffice --convert-to pdf` with a 180 s timeout, checks the `%PDF-` magic (soffice can exit 0 without writing anything), counts slides with `pdfinfo` (max 1000), makes `cover.jpg` from slide 1 with `pdftoppm` (best effort), then deletes the original: only `deck.pdf` is kept and served (`GET /:id/file`, Range, `nosniff` + sandbox CSP, like e-books). Status `converting|ready|failed` + `failure_reason`; a failed deck is visible only to its uploader and admin/operator. Deleting while converting is safe (the job notices the missing row and removes the folder), and `recoverJobs()` in `onStart` re-queues conversions a restart interrupted. ponytail: LibreOffice may fetch linked external images while converting an untrusted deck; run it where outbound traffic is restricted.

Links: `links.ts` (`parseSlideLink`, unit-tested) accepts only https `docs.google.com/presentation/d/<id>` or `/d/e/2PACX-…` and `canva.com/design/<id>/<token>/view|watch`, and **rebuilds** the canonical link and the embed URL from the matched ids (the stored `link` is the canonical page; `embedUrl` is derived from it at read time), so the iframe can only load those two sites. Canva edit links, short links (`canva.link`), other hosts, ports and credentials are refused with a message. The deck must be shared as "anyone with the link can view": that cannot be checked from here, and the embeds were only verified by URL rules, not rendered against the real sites.

Web: `/presentations` is the library (inside the shell; cards poll every 3 s while a deck converts) and `/presentations/:id` the viewer **outside the shell** (full screen), like the e-book reader. File decks use the shared `PdfPagedView` (tap zones, swipe, arrow keys, slider; resume at the saved slide; `?page=N` wins); link decks use a sandboxed iframe (`allow-scripts allow-same-origin allow-popups allow-presentation`, no referrer, no top navigation). The **Presentasi** button fullscreens only the stage (bars disappear; keys and taps keep working, a small counter shows the slide); it is hidden when the browser has no Fullscreen API. `usePresentationViewer` polls while a deck is converting and opens it when ready. Slide **transitions** (`transition` prop of `PdfPagedView`: none/slide/fade/zoom, remembered in `hua-slide-transition`, skipped under reduced motion) are real; PowerPoint's own per-object animations are not (LibreOffice flattens them to the final state). Not built: editing/annotating slides, speaker notes, per-slide thumbnails strip, re-running a failed conversion (delete and re-upload).

## Presence module (`apps/api/src/modules/presence`, web `features/presence`)

Per-class attendance with **WebAuthn passkeys** (the phone's own fingerprint/face/screen lock, `@simplewebauthn/server` + `/browser`). Tables: `webauthn_credentials` (only the public key, base64url), `classrooms` + `classroom_members`, `attendance_sessions`, `attendance_records` (one per user per session; `method` is `webauthn`, `device` is reserved for a future fingerprint machine: no machine endpoint exists). Switched on by Config `biometricsEnabled` (passkey registration and check-in answer 403 when off).

Roles: admin, operator, teacher, student take part (staff do not, as in the nav). Teachers create classrooms and are their owner and only manage their own; admin/operator manage all. Members (students and teachers only) are picked from `GET /presence/people`. A manager opens a **session** (optional auto-close minutes, optional "late after N minutes"; one open session per class); members check in while it is open (open = not closed and `closesAt` not passed; times come from the app clock). Staff-style manual marking is not built.

Check-in is two calls: `POST /sessions/:id/check-in/options` (runs every gate: biometrics on, member, session open, not already checked in, has a passkey, location; returns a challenge) then `POST /sessions/:id/check-in` (re-runs the gates, verifies the signed assertion with `requireUserVerification`, bumps the counter, inserts the record, `late` computed server-side). The relying party is derived from `FRONTEND_URL` (rpID = its host name, origin = its origin), so the browser must run on exactly that origin; passkeys need https except on `localhost`. ponytail: pending challenges are an in-memory map keyed by user (5 min, single use); a restart or a second API instance loses them and the user just taps again. Location: if Config has a school point, the browser's GPS must be within `schoolRadiusM` (haversine, `geo.ts`); it is client-reported, so it deters but cannot prove. Only `distanceM` and the raw coordinates are stored on the record.

Web: `/presence` (inside the shell) has tabs "Kelas" (classroom list + `SessionRoster`, which polls every 5 s while a session is open so the teacher watches check-ins arrive) and "Perangkat saya" (`PasskeyPanel`: register/remove devices). Open sessions of the user's classes show as `CheckInCard`s on top (polled every 15 s); `useCheckIn` does GPS (only when required) -> options -> `startAuthentication` -> verify. Config page: the Fitur section shows the school location (manual lat/lng, "use my location") when biometrics is on. Tested with Chrome's **virtual authenticator** (CDP `WebAuthn.addVirtualAuthenticator`, internal transport, user-verified), not a real fingerprint reader. Not built: reports/export, manual marking, per-subject timetables, anti-spoofing beyond the GPS radius, rate limiting.

## Classes module (`apps/api/src/modules/classes`, web `features/classes`)

School structure on top of Presence's `classrooms`: one model covers the three Indonesian systems. The kind of class is a **school-wide Config setting**, `classSystem` (Config page, Fitur section; applies to every class, `/config/public` exposes it): `homeroom_teacher` (SD **guru kelas**: the class's `homeroomTeacherId` teaches every subject unless a subject has its own teacher, e.g. Agama/PJOK/English) or `subject_teachers` (SMP/SMA/SMK **guru mata pelajaran**: every subject has its own teacher and the homeroom teacher is the **wali kelas**). Tables: `subjects`, `rooms` (`ownerId` = a teacher's own subject room, null = shared), `classroom_subjects` (class + subject + `teacherId`, null = homeroom teacher), `lessons` (weekly slot: weekday 1-7, `startMin`/`endMin` minutes after midnight, `roomId`). **Moving class** is a second Config switch, `movingClass`: while on, a lesson may name a room (students go there; without one the class stays put). While off, rooms are kept in the DB but ignored everywhere: hidden in class details and schedules, never clash, a room in a request is dropped and an update leaves a stored room untouched (the web hides the room picker and the Ruang panel). The old per-class column `classrooms.system` is **unused** (the API reports the school mode as each class's `system`; drop the column in a later migration).

Rules in `service.ts`/`rules.ts`: the lesson's teacher is **derived** (assignment teacher, else homeroom teacher) and never stored, so it cannot drift; `rules.ts` (pure, unit-tested) refuses a lesson that overlaps another lesson of the same class, the same teacher, or the same room on the same day (back-to-back is fine; answers 409 with an Indonesian message), and the same check runs when a subject's teacher or a class's homeroom teacher changes. Switching the school to `subject_teachers` (`PATCH /config`, checked by `classSwitchProblem` in `classes/service.ts`) answers 409 while any subject in any class still has no own teacher; switching to `homeroom_teacher` is always allowed and keeps the teachers already chosen. Only users with role `teacher` can be homeroom/subject teachers or room owners. `STRUCTURE` roles (admin, operator, **staff**) maintain everything (classes, subjects, rooms, assignments, timetable); everyone signed in reads what concerns them (a teacher: classes they own/advise/teach in/belong to; a student: their own); `GET /classes/schedule/mine` is a teacher's or student's week. Class rosters and attendance stay in Presence (admin/operator/teacher manage them); **the homeroom teacher now manages the class's Presence sessions and roster too** (`canManage` in `presence/service.ts` = admin/operator, owner or homeroom teacher). Names of subjects and rooms are unique ignoring case. ponytail: clash check is read-then-write without a lock (two admins editing the same minute could double-book; add a Postgres exclusion constraint if it ever matters); no class delete in this module (Presence's delete still works for admin/operator/owner); no student roster picker here (use Presence); times are the browser's/school's local clock, no holidays or terms.

Web: `useClassMode` reads the two settings from `/config/public`; the class dialog has no type selector (only its wording follows the mode). `/classes` (inside the shell, nav "Kelas & Jadwal", everyone). Tabs: "Jadwal saya" (teachers and students: now/next lesson with "Pindah ke <room>" and the week), "Kelas" (list + `ClassDetail`: assignments and timetable; managers edit), "Mapel & ruang" (`SubjectsPanel`, `RoomsPanel`; managers). `components/ui/BaseSelect.vue` wraps shadcn Select (string values; "none"-style sentinels stand for null).

## Assignments module (`apps/api/src/modules/assignments`, web `features/assignments`)

Homework per **class + subject** (FK to `classroom_subjects`, so unassigning a subject removes its assignments). Tables: `assignments` (title, instructions, `dueAt`, `allowLate`, `maxPoints`), `assignment_submissions` (one per student: text ≤ 10,000, `submittedAt`, `late`, `score`, `feedback`, `gradedAt`), `assignment_files` (owned by an assignment **or** a submission, DB check enforces exactly one; bytes at `UPLOAD_DIR/assignments/<fileId>`).

Who: the teacher who teaches that subject in that class (assignment teacher, else homeroom teacher, same derivation as the timetable) and admin/operator post, edit, delete and grade; students of the class answer; staff take no part (as in Presence). `GET /assignments/targets` gives the classes+subjects a viewer may post to (no import of the classes feature). Visibility is strict: non-members and other teachers get 404, a classmate's answer and files are invisible to other students.

Rules in `service.ts`: deadlines use the app clock; `late = now > dueAt`; with `allowLate` off a submission after the deadline answers 409. A student sends text and/or up to 5 files (`PUT /:id/submission`, multipart: `text`, `keep` = ids of earlier files to keep, `files`); resubmitting **replaces** the answer (kept ids are checked to belong to that submission). Once graded it is locked (409) until the teacher "opens it again" (`DELETE /submissions/:sid/grade` clears score and feedback). Score 0..`maxPoints` (decimals ok); `maxPoints` cannot be lowered below a score already given. Worksheet files (up to 5) are managed with `POST/DELETE /:id/files`. File size per file is the configurable `maxAssignmentMb` (413; also in `/config/public`; effective cap `min(config, MAX_BODY_MB)`). **Files are never rendered inline**: every download is `application/octet-stream` + `attachment` + `nosniff` + sandbox CSP, so the declared type is not trusted or even read; names go through `http/fileName.ts` (`cleanName`, shared with chat). ponytail: files of assignments removed *indirectly* (their class or subject deleted) stay on disk as orphans (rows cascade, bytes do not); a sweep can remove ids without a row. Not built: notifications/reminders, rubrics, group work, per-student extensions, plagiarism checks, exporting grades (CSV like CBT would be the natural next step), the late flag is not shown as minutes late.

Web: `/assignments` (list: "Belum lewat tenggat" / "Lewat tenggat", badges per role: a student's state, a teacher's `submitted/total · graded`) and `/assignments/:id` (inside the shell, nav "Tugas"). A student sees instructions, worksheet and the `SubmissionForm` (read-only once graded or closed, showing score and feedback); a manager sees the roster (`SubmissionsTable`, includes students who have not answered) and opens `GradeDialog`. The class page shows the class's assignments through a slot: `pages/ClassesPage.vue` fills `ClassesView`'s `class-extra` slot with `ClassAssignmentList` (a page assembles features; neither imports the other). Verified with 69 API checks over real HTTP and a 25-step headless browser run (teacher posts, student answers on a phone, grading, reopen, late/closed, delete).

## Rules (follow strictly; do not invent new patterns or folders)

### Web stack
Vue 3 Composition API with `<script setup lang="ts">` ONLY; strict TypeScript (no `any`); Tailwind + shadcn-vue utility classes (avoid `<style>` unless needed for complex animation); Pinia **setup stores** only; Vue Router; icons from `lucide-vue-next`.

### Web folder structure (`apps/web/src`)
```text
assets/        global CSS, fonts, static images
components/    domain-agnostic UI: ui/ (shadcn primitives), layout/ (AppSidebar.vue, AppHeader.vue)
composables/   app-wide generic composables (useToast.ts, useDebounce.ts)
features/<name>/{components,composables,services,stores,types.ts}   isolated business domains
pages/         route-level views: thin wrappers that assemble features
router/        route definitions + guards
services/      core API client (api.ts, Eden Treaty) and realtime client (socketClient.ts)
utils/         pure helpers (cn.ts, formatters)
```
- **Pages are thin**: layout assembly + route params only; no API calls or complex logic.
- **Feature isolation**: feature A never imports from feature B's `components/` or `services/`; promote shared code to `src/components/` or `src/composables/`.
- Flow: `.vue` → composable → feature service (`xxxApi.ts`) → core client (`services/api.ts`) → backend. `.vue` files do rendering and events only.
- Naming: components `PascalCase.vue` (own primitives start with `Base`; shadcn-generated primitives in `components/ui/` keep shadcn's names); composables `useXxx.ts`; services `xxxApi.ts`/`xxxService.ts`; stores `useXxxStore.ts`; types/interfaces `PascalCase`, no `I` prefix.
- `.vue` order: `<script setup lang="ts">`, `<template>`, `<style scoped>` (only if required). Script order: imports (external → shared → feature-local → types), typed `defineProps`/`defineEmits`, composables/stores, reactive state, computed, functions/handlers, lifecycle hooks and watchers.
- Keep template expressions simple (move logic to `computed`). Components showing fetched data must handle loading, error and empty states.

### Realtime
One client instance, created in `src/services/` (`socketClient.ts`); never connect inside `.vue` files. Manage subscriptions in a feature composable (e.g. `features/chat/composables/useChatRoom.ts`); every listener added in `onMounted` MUST be removed in `onUnmounted`. On realtime `INSERT` events, check message `id` before pushing so the sender's own message isn't rendered twice.

### API structure (`apps/api/src`)
```text
db/{index.ts,schema.ts}              Drizzle + PostgreSQL (snake_case columns)
modules/<feature>/{index.ts,service.ts}   index.ts = Elysia routes + validation, service.ts = business logic + DB queries
plugins/                             auth macro, CORS, error handler
index.ts                             app entry, exports `type App`
```
Backend modules mirror web features (chat's `index.ts` also has the `.ws()` handler).

### Workflow
Before writing code for a new feature: list the exact file paths to create/modify, say how they fit the structure above, and **wait for confirmation if more than 3 files change**.

### Gotchas
- **`app.handle()` is not the real server**: it hides Bun-specific behavior (e.g. a `params: t.Object({ id: t.Numeric() })` schema returned 500 on a real server but passed every `app.handle` test; Elysia 1.4.32 tries to rewrite Bun's frozen params, so ids are parsed by hand). Keep at least one test going through `app.listen(0)` + `fetch` per kind of route, and e2e-check new modules over real HTTP.
- pdf.js v6: close a document with `pdf.loadingTask.destroy()` (there is no `pdf.destroy()`).
- Elysia's `app.handle(new Request(...))` returns 404 for very short hostnames (`http://x/...`); use `http://localhost/...` in tests.
- Cookies ignore ports: TekSso and other local apps share the `localhost` cookie jar, hence the `hua_` cookie prefix.
